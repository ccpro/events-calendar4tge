# Executive Project Brief

### 🎯 Purpose

A web application built for tabletop card game store organizers to schedule in-store trading card game events (e.g., _Magic: The Gathering_, _Pokémon TCG_, _One Piece Card Game_) and manage player registrations with server-enforced capacity control.

### 🛠️ Tech Stack

- **Framework**: Next.js 16 (App Router) & React 19
- **Language**: TypeScript
- **Database**: SQLite (`better-sqlite3`)
- **Styling**: Vanilla CSS Modules
- **Key Libraries**: `ics` (Calendar Invites), `react-qr-code` (Mobile Check-in QR Codes), `vitest` (Testing)

### ⭐ Core Features

1. **Event Scheduling**: Create events with custom dates, formats, durations, and capacity limits (up to 30 players).
2. **Extensible Template System**: Game configurations (formats, min/max players, durations) are defined via JSON templates (`public/templates/`).
3. **Calendar View & ICS Export**: Visual monthly calendar grid with downloadable `.ics` calendar files importable into Google Calendar & Outlook.
4. **Capacity-Enforced Player Registration**: Registration links and QR codes allow players to sign up with server-side validation against event full/duplicate states.

### 🏗️ Key Architecture Highlights

- **Zero Database Setup**: Auto-initializes SQLite database (`dev.db`) on startup.
- **Server-Side Capacity Validation**: Prevents overbooking at the API route layer (`/api/events/assign/...`) using SQLite transaction queries and unique composite indexes `(gameEventId, playerId)`.
- **Role Context**: Manages client role state (`Organizer` vs `Player`) via `SelectedRolesProvider` synchronized with `localStorage`.

### 1. Architectural Overview

The application is built on **Next.js 16 (App Router)** with **TypeScript**, **SQLite** (`better-sqlite3`), and **Vanilla CSS Modules**. It allows store organizers to manage tabletop trading card game events (e.g., Magic: The Gathering, Pokémon TCG, One Piece) and enables players to register for scheduled events with server-enforced capacity limits.

---

### 2. API Layer (`src/app/api/...`)

All backend endpoints are built using Next.js App Router Route Handlers (`route.ts`). Database operations run synchronously against SQLite via [db.ts](file:///c:/tmp/hasbro/events-calendar4tge/src/app/api/_lib/db.ts).

| Endpoint                                        | Method        | Description                                                                                                                   |
| :---------------------------------------------- | :------------ | :---------------------------------------------------------------------------------------------------------------------------- |
| **`/api/events`**                               | `GET`         | Retrieves all scheduled game events along with assigned player counts and active player assignment status.                    |
| **`/api/events`**                               | `POST`        | Creates a new game event with validations for start date (must be in the future), capacity (1–30), duration, and game format. |
| **`/api/events/assign/[eventId]/[playerId]`**   | `POST`        | Assigns a player to an event. **Server-enforces capacity** and checks for duplicate registrations.                            |
| **`/api/events/unassign/[eventId]/[playerId]`** | `POST`        | Removes a player from an event.                                                                                               |
| **`/api/events/players/[eventId]`**             | `GET`         | Fetches the list of registered players/attendees for a specific event.                                                        |
| **`/api/games`**                                | `GET`, `POST` | Lists existing game types or creates new custom game types linked to a template.                                              |
| **`/api/games-templates`**                      | `GET`         | Reads JSON template configuration files dynamically from `public/templates/`.                                                 |
| **`/api/player` & `/api/player/[uuid]`**        | `GET`         | Retrieves all registered players or registers/retrieves a player by UUID.                                                     |
| **`/api/organizer`**                            | `GET`         | Retrieves available event organizers from the database.                                                                       |
| **`/api/ip`**                                   | `GET`         | Returns the host machine's local IPv4 address for QR code registration URL generation.                                        |

### 3. Middleware, Context & Data Persistence

- **No Next.js Edge Middleware**: The application does not use a standalone `middleware.ts` file. Request validation, capacity checks, and authorization rules are handled directly inside each API route handler.
- **Global Role Context**: State management for active roles is handled via [SelectedRolesProvider.tsx]. It synchronizes the current active role (`activeOrganizer` / `activePlayer`) between React State and `localStorage`.
- **Database & Schema Bootstrap**: SQLite database setup and migration scripts reside in [db.ts]:
    - `role`: Stores organizers (`roleType = 1`) and players (`roleType = 2`).
    - `game_type`: Stores game definitions, durations, formats, and template identifiers.
    - `game_event`: Stores scheduled events with start times, capacities, and formats.
    - `game_event_players`: Maps players to events with a **unique constraint** `(gameEventId, playerId)`.

### 5. Core Business Logic

#### A. Capacity Enforcement

Capacity enforcement is implemented at the server/API layer inside [route.ts]:

1. **Capacity Query**: Queries `playersAssigned` vs `playerCapacity` before processing assignment. If `playersAssigned >= playerCapacity`, returns `HTTP 409 Conflict`.
2. **Duplicate Registration Protection**: Queries `game_event_players` table and throws `HTTP 409 Conflict` if the player is already signed up.
3. **Database Unique Index**: SQLite enforces `UNIQUE(gameEventId, playerId)` at the DB layer as a fallback safety guard.

#### B. Dynamic Game Template System

Templates live as JSON files under `public/templates/`:

- [mtg-template.json](file:///c:/tmp/hasbro/events-calendar4tge/public/templates/mtg-template.json)
- [pokemon-template.json](file:///c:/tmp/hasbro/events-calendar4tge/public/templates/pokemon-template.json)
- [one-piece-template.json](file:///c:/tmp/hasbro/events-calendar4tge/public/templates/one-piece-template.json)
- [default-template.json](file:///c:/tmp/hasbro/events-calendar4tge/public/templates/default-template.json)

Each template defines event properties such as default duration, capacity bounds (`min`/`max`), required fields, and game formats (`Standard`, `Commander`, `Expanded`, `Arena-style`). Adding a 4th game requires adding a JSON file in `public/templates/` without changing core event logic.
